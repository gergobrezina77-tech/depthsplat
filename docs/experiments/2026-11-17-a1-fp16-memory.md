# Approach 1: FP16 and Training Memory

Date: 2026-11-17. Branch `a1-memory-experiments` (worktree `~/projects/depthsplat-a1-fp16`, based on `efff019`).
Commits: `f61ac14` (FP16 mixed precision, 3-scene varying-budget run, peak memory report),
`1004237` (FP16 storage of activations kept for backward).

## 1. Summary

- Training memory is dominated by **activations**, not by the model. The model is ~200 MiB
  (weights 146 MiB + LPIPS VGG 56 MiB); one training step peaks at ~5.4 GB.
- **FP16 mixed precision** (`16-mixed`) cuts the peak by only **7.4%** (5,385 → 4,987 MiB) and trains
  ~11% faster. The CUDA rasterizer and much of LPIPS stay FP32.
- **Storing kept activations as FP16** (`fp16_saved_activations`) cuts the allocated peak by **20%**
  (5,385 → 4,282 MiB) with identical training results (val PSNR within 0.01 dB) and ~4% slower steps.
  With `expandable_segments` the whole-GPU usage drops by 646 MiB (5,721 → 5,075 MiB).
- The largest single consumer is the **LPIPS loss**: 3.1 GB of the 5.4 GB peak.
- Backward already stops at `gaussian_head`; the frozen encoder costs no backward work.

## 2. Setup

| Item | Value |
|---|---|
| Model | DepthSplat small, 256x256, 2 context views, 38.35M params; only `gaussian_head` trains (56,351 params) |
| Data | 3 scenes of `re10k_overfit5` (`41b80c5f`, `c356b5fd`, `3fe0de69`), fixed views, no augmentation |
| Budget | varying, `k ~ U[0.01, 1]` per step (`scripts/a1_overfit3.sh`) |
| Batch | 3 scenes: 6 context images in, 9 target views rendered twice (all Gaussians, then the top-`k` cut) |
| Loss | MSE + LPIPS (0.05) on both renders |
| GPU | RTX 2080 Ti, 11 GB, sm_75 (no bf16) |
| Memory metric | `torch.cuda.max_memory_allocated()` / `max_memory_reserved()` over the run (`peak_memory_train.json`), plus `nvidia-smi` sampled every second |

## 3. What Was Changed

| Change | Where | How |
|---|---|---|
| Precision option | `approach1.precision` (`32-true` default, `16-mixed`) | Passed to the Lightning `Trainer`. `16-mixed` = fp16 autocast + loss scaling; weights, grads and AdamW state stay FP32. |
| FP32 rendering under autocast | `ModelWrapperA1._render` | The rasterizer only accepts FP32 (`RuntimeError: expected scalar type Float but found Half`). Gaussians are cast to FP32 and the decoder runs with autocast off. |
| FP16 storage of saved activations | `approach1.fp16_saved_activations` (default `false`), `fp16_saved_tensors()` in `model_wrapper_a1.py` | `torch.autograd.graph.saved_tensors_hooks`: every FP32 tensor autograd keeps for backward is stored as FP16 and converted back in backward. Skips weights, buffers and non-float tensors. A cache (with a weakref guard) stores one copy per tensor that several ops save. |
| Peak memory report | `src/approach1/train.py` | Writes `peak_memory_train.json` after `fit`. |
| Test | `tests/approach1/test_fp16_saved_tensors.py` | Gradients with and without FP16 storage match within 1%. |

Usage:

```
PRECISION=16-mixed scripts/a1_overfit3.sh <out>
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True scripts/a1_overfit3.sh <out> approach1.fp16_saved_activations=true
```

## 4. Results

### 4.1 Peak memory over a run (MiB)

| Run | Steps | Peak allocated | Peak reserved | `nvidia-smi` | Steps/s |
|---|---|---|---|---|---|
| FP32 baseline | 300 | 5,385 | 5,428 | 5,745 | 1.31 |
| FP16 mixed precision | 3000 | 4,987 (−7.4%) | 5,088 | n/a¹ | 1.46 |
| FP32 + FP16 storage | 300 | 4,282 (−20.5%) | 5,126 | 5,443 | 1.26 |
| FP32 + `expandable_segments` | 300 | 5,362 | 5,404 | 5,721 | n/a |
| FP32 + FP16 storage + `expandable_segments` | 300 | 4,258 (−20.9%) | 4,758 | 5,075 (−646) | n/a |

¹ Contaminated: a separate probe ran on the GPU during that run.

Training quality: FP32 + FP16 storage matches the FP32 baseline at val steps 99/199/299 within
0.01 dB (k = 1.0, 0.5, 0.1), no NaN. The FP16 mixed-precision run had no NaN over 3000 steps;
val PSNR at step 2999: 30.28 (k=1.0), 24.83 (k=0.5), 16.65 (k=0.1). Its first 300 steps track
the FP32 run within ~0.4 dB (differences also come from the longer OneCycle schedule).

## 5. Why FP16 Does Not Halve Memory

- Only activations shrink; the model is ~4% of the peak.
- FP16 mixed precision only computes convs/linears in FP16. The rasterizer is FP32-only, and LPIPS
  normalizes its features with sums, square roots and divisions that autocast keeps in FP32. So
  LPIPS (57% of the peak) shrinks only 14%, the renderer 0%, the encoder 43%.
- FP16 storage shrinks kept tensors by ~40%, not 50%: integer/byte buffers (rasterizer tile lists,
  sort keys, max-pool indices) and weights are not packed.
- The peak falls inside the second LPIPS forward. Its working tensors exist in FP32 while computed;
  packing only changes how results are stored afterwards, and briefly needs both copies (+330 MiB
  temporary).
- Without `expandable_segments`, the PyTorch caching allocator keeps most of the freed memory
  reserved (fragmentation), so `nvidia-smi` only drops ~300 MiB.

## 6. Checked: No Wasted Backward

The backward graph of one step was walked from the loss. Only the 4 `gaussian_head` tensors receive
gradients; 20 of 141 conv layers appear (2 in `gaussian_head`, 18 in LPIPS: 13 VGG convs + 5 1x1
weighting layers), none from the encoder. Autograd only records ops with an input that requires grad;
the frozen encoder (`requires_grad=False` via `freeze_all_but`) is never recorded. LPIPS VGG weights
are buffers, so only input gradients (needed to reach the render) are computed there.
Open: one non-parameter leaf tensor in the graph is unidentified (a single tensor, not a layer).

## 7. Future Work

| Idea | Expected effect | Risk / cost |
|---|---|---|
| Gradient checkpointing of LPIPS | Removes most of the 3.1 GB LPIPS kept features; recomputes VGG in backward | ~1 extra VGG forward per step |
| LPIPS on fewer views or only on the cut render | Linear in LPIPS images | Changes the loss |
| Frozen encoder in true FP16 (`.half()`, no autocast) | Halves its ~3.3 GB temporary peak, which is the floor (~3.7 GB) once LPIPS is fixed | Small depth/Gaussian differences; check vs FP32 |
| LPIPS VGG in true FP16 | Halves LPIPS working memory | `normalize_tensor` (sum of squares, `eps=1e-10`) can overflow/underflow; needs an FP32 normalization |
| FP16 storage + `16-mixed` together | Measured in one step: peak 4,136 vs 4,185 MiB | Little gain over FP16 storage alone |
| `save_on_cpu()` instead of FP16 storage | Moves kept tensors to host RAM | Slower (PCIe copies) |
| Smaller batch | Linear in all activations | Noisier gradients, longer runs |
| Apply to Approach 2 (`src/approach2`) | Same LPIPS-dominated profile expected | Not measured |
